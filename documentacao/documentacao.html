Resumo

Em uma página

Buracos, alagamentos e semáforos apagados só entram na fila de reparo de São Paulo quando alguém reclama. O Olho na Via instala um dispositivo IoT em ônibus e nos veículos de voluntários para que a própria rua avise a Prefeitura.

Esta entrega é o sensor do projeto: um ESP32 simulado no Wokwi que lê acelerômetro, ultrassom, luz, GPS e bateria, suaviza as leituras, descarta valores inválidos e escolhe entre 4 estados. A resposta é local (LEDs, buzzer, LCD e “foto”) e acontece mesmo sem rede.

Com conexão, os eventos seguem por MQTT no padrão UltraLight do FIWARE até o painel do gestor e o app do cidadão. Sem conexão, ficam numa fila offline e são enviados quando a rede volta.

4 estados
NORMAL, ATENÇÃO, CRÍTICO e FALHA, cada um com resposta própria
100 ms
ciclo de leitura com millis(), sem travar o loop
5 + 3
leituras na média móvel e leituras seguidas para confirmar o estado
10 eventos
guardados na fila offline enquanto o veículo está sem cobertura

01
Problema e conexão com a CitizenTech

A rua avisa antes de alguém precisar reclamar

Em 2025, o SP156 recebeu 113,1 mil pedidos de tapa-buraco, e 38% dos pedidos do 1º semestre de 2026 ainda estavam sem atendimento em agosto. Enchentes e alagamentos subiram 47% em 2025 e as falhas em semáforos chegaram a 17,5 mil por ano. Em todos os casos, o reparo começa só quando alguém reclama.

O problema em uma frase: buracos, alagamentos e semáforos apagados só entram na fila de reparo quando alguém reclama, e ninguém confere se o conserto foi feito.
Quem é o cidadão

Quem usa a rua todo dia

Passageiros, pedestres (principalmente idosos), ciclistas e motociclistas, que são os mais expostos a cada defeito. Do outro lado, a gestora da subprefeitura, que precisa saber o que é mais grave.

Onde o dispositivo fica

Ônibus e Kit Cidadão

Atrás do para-brisa dos ônibus que já circulam pela cidade, ligado nos 24 V do veículo. A versão Kit Cidadão, com bateria, vai no carro ou na moto de voluntários (taxistas, entregadores).

Por que na borda

A rede falha onde o problema está

Túnel, garagem, enchente e periferia com 4G fraco. O dispositivo decide e reage sozinho, guarda o evento e envia quando a cobertura volta.

2.1 O ciclo que roda dentro do ESP32
1

Medir

Impacto vertical, lâmina d'água, luz, bateria, sinal de GPS e de rede.

2

Decidir

Valida cada leitura, suaviza, compara com os limites e confirma o estado.

3

Alertar

LED da cor do estado, buzzer no CRÍTICO, mensagem e valor no LCD.

4

Atuar

Captura a foto, monta o evento com GPS e envia ou guarda na fila.

2.2 Online e offline

Com rede

Telemetria a cada 5 s e um evento a cada mudança de estado no tópico /TEF/olhonavia001/attrs. O IoT Agent converte o UltraLight em atributos da entidade no Orion, e o painel lê o contexto atualizado.

O dispositivo também escuta /TEF/olhonavia001/cmd: o gestor pode pedir uma foto remota do ponto.

Sem rede

Os LEDs, o buzzer e o LCD continuam reagindo, porque a decisão é local. Cada evento vai para a fila offline (o LCD mostra OFF F3, por exemplo).

Quando a conexão volta, a fila é enviada na ordem em que os eventos aconteceram. Se encher, o evento mais antigo sai para dar lugar ao novo.

Por que só eventos? Enviar vídeo de mil ônibus pelo 4G seria caro e arriscado para a privacidade. Do dispositivo sobem apenas estado, motivo, medidas, posição e o nome de uma foto já anonimizada na borda (rostos e placas desfocados).
03
Do hardware planejado ao simulado

Cada peça do Wokwi representa uma peça real

O dispositivo físico foi planejado com ESP32, ESP32-CAM, MPU-6050, placa TTGO T-Beam (bateria, GPS e LoRa) e um painel LCD. O Wokwi não tem câmera, GPS, LoRa nem bateria, então cada recurso ausente foi trocado por um componente que mostra o mesmo comportamento na simulação.

3.1 Por que cada componente está ali

Sensores: o que a rua “sente”

  • MPU-6050: o buraco aparece como um pico de aceleração vertical, sem depender de imagem nem de luz.
  • HC-SR04: mede distância sem contato com a água, o que serve para lâmina d'água.
  • LDR: é a forma mais simples de saber se há luz no semáforo.
  • GPS e bateria: sem posição o evento não vale; sem bateria o kit para.

Interface: o que as pessoas veem e ouvem

  • LEDs: um olhar basta para saber o estado, inclusive para o motorista.
  • Buzzer: só no CRÍTICO, para não virar ruído na rotina.
  • LCD: mostra o motivo e o valor, útil para o técnico e para o vídeo.
  • Botão: dá voz ao voluntário quando o sensor não vê o problema.

05
Lógica de borda

Limites justificados e quatro estados

Os limites são iniciais, escolhidos para a simulação a partir do uso real de cada grandeza. No piloto, serão recalibrados com dados dos ônibus (tipo de veículo, velocidade e suspensão). Todos estão em constantes no início do sketch.ino.

GrandezaLimitesJustificativa
Impacto |Δaz|
aceleração vertical − 1 g		ATENÇÃO ≥ 0,4 g
CRÍTICO ≥ 1,0 g		Parado ou em asfalto liso, o eixo Z mede 1 g. Abaixo de 0,4 g de variação ficam as vibrações comuns do veículo; acima de 1,0 g, a roda caiu num buraco capaz de derrubar uma moto. Valores iniciais, a calibrar no piloto.

Prioridade da decisão: FALHA vem primeiro (sem dado confiável não há decisão), depois CRÍTICO, ATENÇÃO e NORMAL. Entre as causas críticas, a ordem é buraco, alagamento e semáforo.

5.2 Leitura inválida, suavização e confirmação
Validar

Descartar o que não é físico

Cada sensor tem uma flag (impactoValido, aguaValida). Sem resposta do MPU-6050, valor fora da escala ou ultrassom sem eco, a leitura não entra na média e o estado vai para FALHA. O MPU-6050 é reconectado a cada 5 s.

Suavizar

Média móvel de 5 leituras

Três vetores guardam as últimas 5 leituras de impacto, água e luz (0,5 s). A função calcularMedia() soma e divide. Uma vibração isolada não muda a média o suficiente para mudar o estado.

Confirmar

3 leituras seguidas

O novo estado vira “candidato” e só é aceito depois de 3 leituras iguais (0,3 s). É uma histerese no tempo: evita o LED piscando e eventos repetidos quando o valor fica perto do limite.

5.3 O loop, sem delay()
Sempre
Verifica o botão (borda de descida + 300 ms), atualiza LEDs e buzzer e chama mqtt.loop().
100 ms
lerSensores() → decidirEstado() → confirmarEstado(). Se confirmou, mudarEstado() registra o evento.
250 ms
atualizarLcd(): estado, rede e tamanho da fila na linha 1; motivo e valor na linha 2.
5 s
Avança o GPS na rota, tenta (re)conectar o MQTT, envia a fila e publica a telemetria.
Evento
registrarEvento() monta a mensagem e publica, ou guarda na fila se estiver offline.
Por que millis()

Cada tarefa compara millis() com o último instante em que rodou. Assim a leitura não espera o LCD, o buzzer não trava o botão e a reconexão não congela os alertas.

Os únicos atrasos são de microssegundos: o pulso de 10 µs do HC-SR04 e a espera do eco, limitada a 30 ms em pulseIn().

5.4 Trecho central: a decisão
int decidirEstado() {
  if (!impactoValido) { motivo = "acelerometro"; mensagemLcd = "Falha IMU"; return FALHA; }
  if (!aguaValida) { motivo = "sensor_agua"; mensagemLcd = "Falha ultrassom"; return FALHA; }
  if (!gpsComSinal) { motivo = "gps_sem_sinal"; mensagemLcd = "GPS sem sinal"; return FALHA; }
  if (bateria < BATERIA_MINIMA) { motivo = "bateria_baixa"; ... return FALHA; }

  if (impacto >= IMPACTO_CRITICO) { motivo = "buraco"; ... return CRITICO; }
  if (agua > AGUA_CRITICO) { motivo = "alagamento"; ... return CRITICO; }
  if (tempoEscuro >= TEMPO_SEMAFORO_APAGADO) { motivo = "semaforo_apagado"; ... return CRITICO; }
  if (impacto >= IMPACTO_ATENCAO) { motivo = "irregularidade"; ... return ATENCAO; }
  if (agua >= AGUA_ATENCAO) { motivo = "agua_na_via"; ... return ATENCAO; }
  if (tempoEscuro > 0) { motivo = "luz_fraca"; ... return ATENCAO; }
  motivo = "via_ok";
  return NORMAL;
}

Limitações do protótipo
  • A câmera é simulada: o evento leva o nome da foto, não a imagem.
  • GPS em rota fixa; na rua, as coordenadas vêm do módulo real.
  • A média móvel atenua picos muito curtos; na versão final, o impacto usa o valor de pico da janela.
  • Limites calibrados para a simulação, não para um ônibus real.
Próximos passos
  • Montar o protótipo físico e gravar uma volta de ônibus para calibrar os limites.
  • Subir o FIWARE na VM e trocar o broker público pelo IoT Agent.
  • Ligar o painel do gestor (React) à entidade OlhoNaVia no Orion.
  • Detecção de buracos por imagem (IA) para confirmar o acelerômetro.
Privacidade por padrão: a câmera olha o asfalto, não as pessoas. Rostos e placas são desfocados no próprio dispositivo, e só sobem a foto anonimizada e os dados do evento. Não há reconhecimento facial nem leitura de placas.

Conclusão

Um sensor que decide sozinho e ajuda o bairro inteiro

O dispositivo transforma um ônibus que já passa pela rua num fiscal da cidade. Ele percebe o buraco, a água e o semáforo apagado, decide na hora, avisa quem está perto e, quando há rede, entrega à Prefeitura um evento com posição, gravidade e foto. Sem rede, nada se perde.
